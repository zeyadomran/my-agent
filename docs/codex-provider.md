# Codex provider

Issue #4 adds the main-only `createCodexAdapter(options?)` factory in [codex.ts](../src/main/providers/codex.ts), implementing the existing [ProviderAdapter contract](../src/shared/contracts.ts). It uses the [shared runtime](../src/main/providers/README.md); application-service wiring belongs to the integration issue. There is no renderer tool bridge or configuration-management feature.

## Native protocol and configuration

The implementation was checked against the installed Codex CLI **0.163.0**, including its locally generated stable and experimental TypeScript schemas. Initialization accepts the 0.163.x protocol family; other versions fail with `unavailable`. Other patch versions have not been live-qualified. The adapter performs `initialize`, `initialized`, an authentication-status probe without refresh, and an effective `config/read`. It never reads credential files, logs provider output, starts a login flow, writes user configuration, or substitutes a direct API/provider/model.

Profiles select an executable, literal arguments, environment overrides, working directory, and optional model. The shared launcher handles native executables and recognized npm shims without a shell. Arguments may include optional `app-server`, `--stdio`/`--listen stdio://`, `--strict-config`, `-c`/`--config`, and supported `--enable`/`--disable` feature switches. Long options accept `=value` as well. Configuration arguments permit `model`, `model_provider`, `model_reasoning_effort`, `service_tier`, and the explicitly controlled keys in [codex-policy.ts](../src/main/providers/codex-policy.ts). Other commands, transports, or configuration keys fail before launch. Reasoning effort remains configurable and is not treated as a permission control. The profile's model, when present, must match the native setup response.

Application policy is appended after profile arguments and reapplied through native start/resume configuration. It disables the supported shell, execution, image, browser, web, application, connector, plugin, hook, skill-discovery, memory, multi-agent, goal, and related autonomous features; automatic skill instructions, bundled/cloud skills, project instruction loading, notifications, update checks, analytics, and feedback are disabled. Effective MCP server names, plugin IDs, and explicit skill selectors are disabled without copying protected values into session metadata. Configuration values remain inside main and the owned provider process.

Every new native thread uses experimental `environments: []` and `selectedCapabilityRoots: []`. Every `turn/start` also sends `environments: []`; resumption has no equivalent environment override in this protocol. Setup requests require `approvalPolicy: "never"`, reviewer `user`, and a read-only sandbox. The native response must acknowledge that policy, including disabled sandbox network access. Each turn repeats those restrictions. Command/file approvals are declined, MCP elicitations are declined, other client requests receive method-not-found, and unexpected native tool requests/items fail the run and retire its process. Probes also refuse unexpected tool activity.

These controls are restrictive chat policy, **not a guarantee that the native runtime removes every builtin or intercepts every action it already permits**. The native protocol exposes no general client deny-all tool ceiling. Read-only sandboxing alone is not a no-tools policy, and a tool notification may arrive after provider-side activity. No destructive live probes were used to test that boundary.

## Transcript and lifecycle

Each run owns a short-lived app-server process and a persistent native thread. Session metadata contains only native/configuration identifiers and the last incorporated app message ID. Native history is never rendered or appended to the app transcript. A matching checkpoint resumes by `threadId` with `excludeTurns: true`, then supplies only app messages after its marker plus the current prompt. Provider handoff preserves complete available messages using the shared `transcriptPrompt`; exceeding its encoded transport budget fails explicitly without silently trimming history.

A metadata-only `thread/read` precedes reuse. For that fixed valid request, the installed protocol reports a missing native thread as invalid-request (`-32600`); this starts one fresh thread with the complete available app transcript. Other errors, including resume/configuration errors, fail rather than trigger speculative recovery. Mismatched provider/profile/configuration identifiers or unavailable app markers also start fresh.

Before submitting input, a non-reusable checkpoint (`lastMessageId: null`) waits for the consumer's next iteration after persistence. Cancellation, failure, or an abandoned iterator therefore cannot reuse partially mutated native history. A successful assistant marker is checkpointed only after native completion and owned-process retirement. Consumers must persist session events before requesting the next event.

Thread, turn, and text-item identities are correlated. Stream deltas and final text suffixes are emitted once; reasoning and compaction records do not become assistant text. Native compaction does not erase the permanent app transcript. The current shared event contract has no separate compaction/status event. A turn retains at most 512 KiB of assistant text and 256 items, alongside the shared transport limits.

Cancellation attempts `turn/interrupt` for the owned active turn, then closes the process even when interruption fails. Defaults are 10 seconds per setup/RPC request, 120 seconds per turn, and 1 second for interruption, followed by the shared bounded retirement procedure. Disposal aborts active runs, releases checkpoint waits, and drains all owned connections. Exactly one terminal event follows cleanup; shutdown failure is reported as failure rather than successful cancellation.

## Validation and limits

[codex.test.ts](../src/main/providers/codex.test.ts) owns the canonical external-process connection/chat/resume/cross-provider-handoff/stale-recovery/stop flow, with real shared modules and an owned temporary native-session store. Separate cases cover material authentication, protocol, permission, model, process-exit, timeout, and disposal failures. [codex-policy.test.ts](../src/main/providers/codex-policy.test.ts) owns argument/integration binding; [codex-wire.test.ts](../src/main/providers/codex-wire.test.ts) retains only distinct parser resource/lifecycle failures. Fixtures contain synthetic data. Retirement is checked before cleanup by unique fixture instance, retaining confirmed exit facts so PID recycling cannot revive an earlier instance.

A bounded source-level Windows check with the existing authenticated CLI 0.163.0 passed: an ephemeral connection probe, one harmless text prompt, and a second harmless prompt after reopening the same native thread. The smoke used an owned temporary working directory, preserved authentication/configuration, and published only pass/fail evidence. It did not qualify live cancellation, destructive permissions, other models/CLI versions, packaged Codex interoperability, or native Electron UI behavior. Package construction and hosted CI are separate validation evidence.
