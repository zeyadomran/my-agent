# Provider runtime

This main-only runtime implements the [provider contracts](../../shared/contracts.ts). The [application service](../../../docs/application-service.md) connects its Codex, Claude Code, and ACP adapters to durable storage and the renderer through the narrow preload bridge; native processes and session metadata stay in main.

## APIs for adapter consumers

- `createProcessTransport(profile, { onLine, onFailure, onExit? })` in [process-transport.ts](process-transport.ts) launches a resolved profile with literal argv, inherited environment plus profile overrides, bounded UTF-8 line framing, bounded writes, sanitized failure, and idempotent `close()`. Always await `close()` in `finally`. A failure also starts retirement automatically. `endInput()` sends EOF without starting a forced-retirement timer and rejects subsequent sends. If supplied, `onExit(code, signal)` reports natural exit after streams fully drain, and the consumer interprets both zero and nonzero status. Natural exit is not additionally `onFailure` in that mode. Explicit close/transport faults use retirement/failure instead of the natural-exit callback. Without `onExit`, unexpected process exit remains a failure, as required by ACP RPC. The Windows supervisor propagates the actual provider exit status.
- `createRpcTransport(profile, options)` in [rpc-transport.ts](rpc-transport.ts) adds `request(method, params, timeoutMs?)`, `notify(method, params)`, and `close()`. Requests default to 10 seconds; at most 16 may be outstanding. `onRequest` is synchronous; returning `undefined` rejects the method. `onNotification` is synchronous. `onFailure` reports unexpected connection failure even after all RPC responses have resolved. Explicit close rejects outstanding requests but does not call `onFailure`.
- `RpcTransportOptions.dialect` defaults to `jsonrpc2`: incoming frames must contain `jsonrpc: "2.0"`, and outgoing frames include it. Explicit `codex` mode omits the member on outgoing frames, accepts its absence or `"2.0"` on incoming frames, and rejects conflicting values. ACP always uses the default strict dialect.
- `ProviderFault` exposes only `unavailable`, `input-too-large`, or `provider-failed`; `RpcResponseFault` additionally preserves a numeric `rpcCode`. Messages, error data, stderr, arguments, environment values, and native exceptions are never attached to public failures or logged.
- `EventChannel` in [event-channel.ts](event-channel.ts) provides `push(event)`, `checkpoint(event, signal)`, `finish()`, and `events()`. Adjacent queued text deltas coalesce in order, without changing text already delivered to the consumer or crossing any non-delta event. The backlog remains bounded to 256 queued entries / 512 KiB of UTF-8 text, including accurate accounting when chunks join a split surrogate pair. An overflow rejects the new event without changing admitted text. `checkpoint` resolves when the consumer advances **after** that session or context event. Consumers must persist each session/context checkpoint before requesting the next event; do not eagerly buffer the iterator ahead of storage. Abort the signal when abandoning a producer that is awaiting a checkpoint.
- `transcriptPrompt(request, afterMessageId, fitsEncodedPrompt)` and `profileFingerprint(profile)` in [transcript.ts](transcript.ts) are reusable main-only helpers. The fingerprint is a configuration hash, never plaintext launch configuration. A missing marker must cause a new native session rather than a full replay into an existing session.
- `createAcpAdapter(options?)` in [acp.ts](acp.ts) implements `ProviderAdapter`. Setup/RPC request timeouts default to 10 seconds. Turn timing is described below. Each probe/run owns its connection. Abort, iterator return, `dispose()`, malformed output, and failed probes retire it. Consume exactly one terminal `completed`, `stopped`, or `failed` event for a fully consumed run.

Codex and Claude Code adapters use the process/RPC helpers independently of ACP. They remain responsible for their own wire protocol, permission policy, session checkpoints, and terminal outcomes.

`ProcessTransport.ready` resolves when the native process has been created under ownership. Native startup has a separate **30 second** deadline; failure, close, abort or disposal rejects pending readiness and retires the owned process. On Windows, the supervisor reports readiness after job assignment and successful thread resume using an opaque per-launch marker on stderr. Launch data and the marker are removed from the environment before the provider inherits it. The bounded stderr scanner retains only a marker-length suffix, never publishes diagnostics, and never forwards stderr as provider protocol or output. On POSIX, native spawn establishes readiness. Finite-process `onExit` still runs only after readiness and stdout/stderr drainage.

RPC requests wait for readiness before sending and starting their existing response timer (10 seconds by default). Requests waiting for startup count toward the existing outstanding-request bound. This separates native startup from provider response time; it does not increase the response allowance or retry failed requests. Raw finite Claude probes retain their existing end-to-end deadline. Claude turns start their inactivity/absolute policy after native readiness; the independent startup deadline remains unchanged.

## Launch and ownership

[launch.ts](launch.ts) resolves commands using the **effective** environment and absolute profile cwd. Main must resolve omitted/relative working directories against its stable workspace base before calling an adapter. Environment names are case insensitive on Windows. Arguments, including empty entries, quotes, whitespace, percent signs, and metacharacters, stay literal.

Windows native executables launch directly through a fixed supervisor. Standard npm Node `.cmd` shims are recognized structurally, never executed: both the older PATHEXT-in-ELSE form and current cmd-shim final-command form are supported. Their existing JS/CJS/MJS target launches with adjacent `node.exe`, otherwise `node.exe` from effective PATH/cwd. Windows extension lookup prefers executable extensions over npm's adjacent POSIX shim. Additional wrapper commands, shebang arguments/environment mutations, arbitrary `.cmd`/`.bat`/`.ps1`, and missing runtimes return sanitized `unavailable`; configure an explicit interpreter and literal arguments for other scripts. JS/CJS/MJS executable entries use the running Node/Electron executable with `ELECTRON_RUN_AS_NODE=1`. npm shims use an actual Node runtime rather than assuming Electron is Node.

[windows-supervisor.ps1](windows-supervisor.ps1) is fixed application code embedded by Vite. It receives launch data through a private JSON environment entry, removes that entry before the provider inherits environment, and uses `CreateProcess` with Windows CRT argument quoting. No profile data is interpolated into PowerShell source. Windows atomically assigns the suspended provider to a kill-on-close Job Object using `PROC_THREAD_ATTRIBUTE_JOB_LIST`, then the supervisor resumes it. This also avoids a create/assign orphan race during startup cancellation. The supervisor closes its non-inherited job handle on root exit, including early root exit with descendants. Killing the supervisor also retires the job; it never looks up or kills a recycled provider PID. Windows 10+, Windows PowerShell and full-language `Add-Type`/Win32 interop are required; restricted systems fail closed. This ownership mechanism is not a security sandbox for the configured executable.

POSIX launches use a detached process group, retired on root exit and shutdown. An independently detached descendant can escape that group; Windows Job Object behavior is the qualified target. Shutdown first gives EOF a 200 ms grace period, then forcefully retires the owned process/group/job and waits for close, with a 5 second failure deadline. It does not claim successful drainage when close fails.

## ACP behavior and limits

The implementation targets stable ACP v1, not draft v2. Initialization advertises no client filesystem, terminal, authentication-terminal, compaction, elicitation, or app MCP capability. `session/new` is baseline v1; `session/load` is sent only when `loadSession: true` is advertised and saved metadata matches the profile and an available transcript marker. Native load replay is suppressed because the original transcript belongs to the app. No `session/resume`, compaction, or other optional capability is claimed.

Each completed native checkpoint contains only a version, session ID, configuration fingerprint, reuse/load flags, and the last incorporated app message ID. Before prompt submission the adapter yields a non-reusable checkpoint and waits for the consumer to advance after persisting it. After interruption, handoff starts a fresh session. A successful turn checkpoints its assistant message after process retirement. A resource-not-found `-32002` load error retries one new session with available app context within the encoded handoff budget; authentication, transport, malformed protocol, and arbitrary provider errors do not trigger that retry.

Text arrives only from live `agent_message_chunk` text updates for the current session. Prompt stop reasons are validated; cancellation yields `stopped`, and the other recognized completion reasons yield `completed`. Native permission requests always receive the ACP `cancelled` outcome; unsupported client methods receive method-not-found. No app tool, filesystem, terminal, or MCP bridge exists. Provider-owned tools configured outside this app remain governed by that provider; this client cannot guarantee interception of actions the provider already permits.

An explicitly selected model requires an advertised select configuration in category `model`, an offered value, and an acknowledged resulting selection. Otherwise it fails rather than silently ignoring the profile's model.

The transport allows **256 KiB per complete encoded JSON line**, **8 MiB total stdout per process**, **256 KiB total discarded stderr**, and **512 KiB queued stdin**. Malformed JSON/UTF-8, oversized output, unsupported protocol versions, and excessive consumer backlog fail and retire the process. The handoff helper measures the exact next serialized adapter envelope, including nested JSON escaping. It preserves all available history that fits; otherwise it selects the maximal recent suffix of whole messages. Saved stopped/failed replies retain their status and entire available text. If the latest historical message cannot fit, it and all earlier history are explicitly omitted. A notice in provider input states the omitted/included counts; a `context` checkpoint persists the same counts on the assistant message before submission, separately from native session checkpoints. The conversation displays this notice after reopen. No individual message or current prompt is sliced, no saved history is deleted, and no summarization call is made. A current request that cannot fit together with the required notice returns distinct `input-too-large` guidance to shorten it. The app transcript is untouched. This byte budget is a transport safety limit, not a claim about any model's context window. Providers may reject smaller inputs for their own context limits.

## Turn activity deadlines

All three adapters allow 120 seconds without meaningful validated current-turn protocol progress, with a separate 30-minute absolute safety cap. Nonempty ACP message/thought text, correlated Codex turn/item transitions and text/reasoning deltas, and validated Claude message/block/text/thinking transitions refresh inactivity. Empty deltas, unrelated notifications, rate-limit/status chatter, raw stdout and stderr do not; malformed or miscorrelated progress fails under the existing parser policy. Reasoning is not displayed as assistant text. No extra provider call, automatic paid retry, or timeout-settings UI is introduced.

The existing `promptTimeoutMs` (ACP/Claude) and `turnTimeoutMs` (Codex) factory seams now set inactivity; `absoluteTimeoutMs` can select a smaller bounded cap for controlled tests. Durations must be positive safe integers, inactivity cannot exceed the absolute cap, and the cap cannot exceed 30 minutes. Timing starts at native turn submission/readiness, after durable context/session checkpoint acknowledgement. Connection/probe, OS startup, setup/RPC response, native interrupt and owned-retirement deadlines are unchanged. An ACP prompt response shares the turn's absolute cap while its inactivity watchdog remains refreshable. Stop/disposal still drain owned processes, and unconfirmed retirement takes precedence over a stopped outcome.

The canonical ACP, Codex, and Claude tests control only time and their actual external subprocesses. Each proves validated reasoning survives the old two-minute boundary, then fails on inactivity despite unrelated traffic. The ACP flow also verifies the shared absolute cap against continuing progress. Existing Stop, disposal and retirement-failure flows remain authoritative.

## Evidence and primary references

[acp.test.ts](acp.test.ts) is the canonical external process flow. It uses the real runtime and [owned Node fixtures](fixtures/acp-agent.mjs), temporary journals, and event-driven cancellation, then verifies process retirement before cleanup. Every fixture process has a unique instance identity. A confirmed `ESRCH` is retained as a terminal fact for that instance; later numeric PID reuse does not revive it. Fresh instances are always checked, including a new instance using an earlier PID. The probe flow simulates PID recycling only at the OS boundary after both real child exits have been verified, and confirms that a fresh live instance still fails retirement. Fixtures contain synthetic text only. There are no GUI tests or internal-module mocks. Hook checks remain separately owned. Live authenticated ACP/provider interoperability and native Electron UI behavior require separate qualification; fixture results do not establish them.

[acp-startup.test.ts](acp-startup.test.ts) owns the distinct startup deadline and cancellation cases. It controls only OS launch and time, holds a real owned process at an explicit startup gate, then uses the real ACP fixture and runtime. Before the fix, advancing the 10-second response allowance while startup was held returned `provider-failed`; after separating readiness it connects successfully. Timeout, abort, disposal and explicit close remain bounded and verify child retirement. The existing canonical flow continues to exercise the actual Windows supervisor, configured response timeout, finite exit status and stdout drainage.

Issue #19's historical Windows run failed its first connection after 10.969 seconds, but its log contains no startup/protocol/retirement phase evidence. The same runtime also passed the Windows suite in another PR and passed the unchanged canonical probe locally. The controlled gate proves that native startup previously consumed the RPC deadline; it does **not** establish why that historical runner was delayed or uniquely explain its failure. Hosted Windows validation of the fix remains a separate check.

Issue #22 concerns a separate journal-observation failure. [journal.test.ts](fixtures/journal.test.ts) holds real file publication at empty and unfinished-append boundaries: the earlier reader parsed an empty snapshot as JSON and could expose an unterminated record. The canonical probe now requests live observation of newline-terminated records only; an unfinished suffix waits for a later filesystem event, without sleeps or read retries. Final retirement reads still parse the full snapshot and all instance/PID assertions remain intact. Malformed published records fail with a fixed parse-phase label; filesystem failures retain only an allowlisted code, with no native message, path or journal content. The historical main run failed after 719 ms with only the generic journal error, so its exact read/parse cause remains unknown. No production provider code changed for this correction.
